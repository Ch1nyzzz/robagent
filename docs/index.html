Ballast · 2026-05-27 Lifecycle-event stabilization of LLM agents

一个 LLM 主 agent 在外，N 个挂在生命周期事件上的 stabilization hook 在内。 外层用一个 coding agent 自动迭代这些 hook —— 在 SOPbench、EnterpriseOps、GAIA 上 各跑 10 iter，最高在 SOPbench/dangerous_goods 把 held-out test 从 72.95% 推到 96.31%。

repo: github.com/Ch1nyzzz/ballast · SUT: deepseek-v4-pro / deepseek-chat / deepseek-v4-flash · proposer: claude-opus

TL;DR

主流"agent 系统"要么是 一个 LLM 在 while-loop 里改进自己，要么是 一张静态的 multi-agent graph。两者都把 LLM 当作不可分割的黑箱。 Ballast 的赌注是第三条路：

  1. 把 capability（能不能做到）和 stabilization（做了能不能稳）严格分开。
  2. capability 长在主 agent 上（工具 / FC loop / system prompt）。
  3. stabilization 用 挂在生命周期事件上的小钩子 实现 —— 每个 hook 是一个 Python 文件，订阅一个 event，返回一个 Decision。
  4. 外层用一个 coding agent (Claude Opus) 自动写、自动评、自动接纳这些 hook。

下面先给三组 benchmark 的结果，再讲为什么是 lifecycle event 而不是别的形态。

系统三层

全部 5 个 sibling（GAIA / SOPbench × 3 / EnterpriseOps × 2 / tau2 / Toolathlon） 共用同一个骨架，只换 SUT、lifecycle event 集合、和 proposer SKILL.md：

  │  Main agent (the protagonist)  ·  agent/base.py, …               │

  │   THIS is where capability lives — never inside hooks.           │
  └──────────────────────────────────────────────────────────────────┘

三层职责严格不重叠：

  • 主 agent：拥有 tools，跑 FC / React loop，是真正在解题的那一个。
  • Component runtime：在 loop 的每个生命周期点 fire 一次 dispatcher， 允许 hook 改 ctx，但 admission matrix 在 load 时就拒掉非法的"改 LLM 决定"。
  • Outer loop：迭代 hook 集合，accept/reject 依据是 train-30 表现； proposer 跑在 docker 里和 main loop 隔离。

Lifecycle 订阅机制

这是 Ballast 区别于其他 agent framework 的核心。下面四节按 为什么 → 有哪些 event → 怎么写 hook → 怎么被拒 的顺序展开。

为什么是 hook，不是 graph node

大多数 "agentic framework" 用 graph：node 是 LLM call 或 tool call，edge 是 message。 这套范式下，要让某个失败模式不再发生，唯一手段是 插一个新 node 截走流量 —— 问题是 node 会接管"做决定"的位置，把主 agent 稀释成 LLM oracle。

Ballast 用 hook：主 agent 该跑的还是跑，hook 只在 已经发生的事件 上插一脚。每个事件都对应主 agent loop 里一个具体的代码位置，dispatcher 在那里 fire 一次，订阅了这个事件的 component 按 priority 排队跑， 返回的 Decision 改 ctx。

关键约束：hook 永远不能"成为主 agent"。induced_rule 类 component 在 admission matrix 里只允许 inject_context， 不能 rewrite / block。 这把"机械地代替 LLM 做决定"这条退化路径在 load 时切断。

Lifecycle events

以 GAIA runtime 为例。事件按 fire 频次分四组：

per-task setup · once per task

  • task_received
  • session_start
  • pre_prompt_build / pre_context_build
  • pre_agent_construct

per-turn · once per FC turn

  • pre_llm_request
  • post_llm_response
  • on_length_truncation (finish_reason=="length")
  • on_empty_response (空 content + 无 tool_calls)

per-tool-call · once per tool

  • pre_tool_use · rewrite tool args / block this call
  • post_tool_use · rewrite result / inject note
  • on_tool_error · 当 tool result 以 ERROR: 开头时合成

per-task exit · once per task

  • pre_answer_emit · 最后一道闸：normalise / block
  • session_end

其他 sibling 各有自己的事件集（tau2 包含 pre_tool_use / post_tool_use / sub-LLM verifier 的 post_llm_response； Toolathlon 把 OpenAI Agents SDK 的 Runner 包装成同一套；EnterpriseOps 在 React loop 的 pre_tool_arg_validation 点 fire）， 但形状是一样的：fire 点对齐主 agent 真实的执行位置。

跨 sibling 共享：

  • ballast/component_runtime_core/dispatcher.py：单进程 Dispatcher，_depth 使用 threading.local()（早期 race 已修）。
  • ballast/component_runtime_core/event_context.py：EventContext 拥有 ctx.chat() / ctx.emit() / shared scratchpads / blocked 信号。
  • shared_types.py：ComponentClass 与 Trust 跨 sibling 字节相等，只保留一份。

Component dataclass

@dataclass(frozen=True, kw_only=True)
class Component:
    name: str                        # 稳定 id，replace 时复用
    cls: ComponentClass              # mechanism_layer | reactive_guard | induced_rule
    listens: str                     # event 名；dispatcher 按这个路由
    matcher: Optional[Callable[[Ctx], bool]]
    handler: Callable[[Ctx], Decision]
    trust: Trust                     # 必填：evidence_anchor + out_of_evidence_probe
    priority: int = 100              # 同 event bucket 内小的先 fire
    emits: tuple[str, ...] = ()      # 自声明会 emit 的自定义 event

每个 component 是一个独立 .py 文件，文件末尾导出 COMPONENT: Component。 工作流 YAML 只记 component 名字列表：

# ballast/workflows/gaia_main.yaml
nodes:
  - length_recovery_guard
  - cuneiform_numeric_decoder
  - exhaustion_answer_recovery
  - final_turn_commit_notice
  - answer_markdown_strip
edges: []
disabled: []

Decision 协议

handler 返回的 Decision 是一个小 ADT。语义随 event 决定，全部在 dispatcher 中央处理：

kindtypical usepayload 在不同 event 上的含义
allow不动—
block终止本步pre_tool_use: 跳过该 tool；pre_answer_emit: ctx.answer ← None
rewrite替换 live payload pre_prompt_build: 新 prompt 字符串
post_llm_response / on_length_truncation: 新 raw content
pre_tool_use: 新 args dict
post_tool_use / on_tool_error: 新 result 字符串
pre_answer_emit: 新 final answer
inject_context叠加，不覆盖 PRE-event: 追加进 system prompt；POST-event: 拼到 result 末尾让 LLM 下一 turn 看到

Admission matrix

load 时校验，不合法的组合直接拒掉，不到 evaluation 阶段：

class它代表允许的 Decision禁止
mechanism_layer把 LLM 在做的确定性活儿搬进 Python（输出规整、参数 schema 校验）allow / rewrite / block—
reactive_guard对观察到的失败做反应（length 截断、empty、tool error）allow / rewrite / inject_context—
induced_rule从历史 trace 总结的策略提示仅 inject_contextrewrite / block ← 这条切断了"hook 接管 LLM"的退化路径

另外每个 component 必填一个 Trust：

  • evidence_anchor：handler 依据什么稳定结构而不是某个 train trace。 合法 anchor：tool 的 JSON schema、LLM API 的 finish_reason 字段、 SOP 文档里的硬阈值、明确的字符串协议。
  • out_of_evidence_probe：当 matcher 命中、但 anchor 不成立时， handler 必须有的 fall-through 行为（一般是 Decision.allow()）。

完整 component 示例

这是 GAIA iter8 接纳的 answer_markdown_strip —— 在 train-30 单步 +4 task， 全文 30 多行： 

"""Strip markdown wrappers around final answer.

flash 经常给 'FINAL ANSWER: **5**' 或反引号包裹的答案。
mechanism_layer · pre_answer_emit · rewrite ctx.answer。
"""
from __future__ import annotations
import re

from agent.component_runtime.types import (
    Component, ComponentClass, Decision, Trust,
)

_WRAPPERS = [
    (re.compile(r"^\*\*(.+?)\*\*$", re.S), 1),  # **x**
    (re.compile(r"^`(.+?)`$",       re.S), 1),  # `x`
    (re.compile(r"^_(.+?)_$",       re.S), 1),  # _x_
]

def _matcher(ctx) -> bool:
    return bool(ctx.answer) and any(p.match(ctx.answer.strip()) for p, _ in _WRAPPERS)

def _handler(ctx) -> Decision:
    s = ctx.answer.strip()
    for pat, g in _WRAPPERS:
        m = pat.match(s)
        if m:
            return Decision.rewrite(m.group(g).strip())
    return Decision.allow()

COMPONENT = Component(
    name="answer_markdown_strip",
    cls=ComponentClass.mechanism_layer,
    listens="pre_answer_emit",
    matcher=_matcher,
    handler=_handler,
    trust=Trust(
        evidence_anchor="FINAL ANSWER format spec in agent/base.py SYSTEM_PROMPT; "
                        "markdown bold/italic/code wrappers are a stable Markdown surface, "
                        "not a train-specific artifact.",
        out_of_evidence_probe="if no wrapper matches, return allow() — original "
                              "answer is preserved verbatim.",
    ),
    priority=80,
)

关注几件事：handler 没有调 LLM；evidence_anchor 锚在 markdown 语法本身而不是 "我在 train trace 里见过这 4 个 task"；out_of_evidence_probe 保证 matcher 出错时 不会破坏原答案。这是被反复强调的 first principle —— code 因为捕捉到稳定结构而留下，不因为拟合最近的失败而留下。

与其他范式的差异

LangGraph / 经典 multi-agent auto-prompt / DSPy 优化器 Ballast
主控位置 graph 上某个 router node 里的 LLM 编译期决定，运行期固定 主 agent 的 FC loop；hook 不抢主控
扩能力 vs 稳能力 混在一起（都靠加 node） 都通过改 prompt 显式分开，admission matrix 强制
修一个 bug 的形态 加 / 改一个 node + edge 重新跑一次 compile 加一个文件 + workflow yaml 加一行
评估单位 整图 整 pipeline 单 hook 的 train-30 Δ
"LLM 兜底"被允许吗 是 — graph 上的 LLM node 默认 unconstrained 是 — prompt 可以无限膨胀 仅在 reactive_guard 上、并且必须有 evidence_anchor
